Choosing the Tech Stack – C# & .NET 10

An honest evaluation of architectural trade-offs and selecting a modern runtime foundation.

Before writing a single line of code, I had to pick the language to build the foundation. Since this project spans a virtual machine, assembler, compiler, and an OS kernel, the scope is massive. I needed a language that would let me focus entirely on systems logic without drowning in language quirks or memory bugs.

Here is the honest, unfiltered breakdown of how I evaluated the options—and why C# emerged as the absolute "best of all worlds" choice for me.

The Contenders

  • Java (My Daily-Driver): This was the most obvious choice for familiarity, but it has one fatal flaw for a systems project: the lack of foundational unsigned types. When you are building a custom 32-bit VM from scratch, you are living in a world of unsigned integers, bytes, and bitwise operations. Forcing Java's signed types to behave like unsigned types is a recipe for endless mental math and bugs. Java was out.
  • C: The classic choice, but a dangerous one for a solo developer. I am not an expert in C. If I chose it, I would spend 70% of my time manually managing memory, chasing down segmentation faults, and debugging memory leaks. As the project scaled, I knew I would likely make a complete mess of the codebase.
  • C++: It brings excellent automatic memory management utilities (smart pointers) and a stellar standard library. However, the footguns remain—you can still easily pass around an invalid pointer and crash the system. Like C, I just don't have the deep familiarity required to shepherd a project of this scale in C++.
  • Rust: An incredible language for systems programming, but the learning curve is steep. There is just too much to unlearn to get productive quickly.
  • Go: A black box to me. Completely unfamiliar.
  • Python: Fantastic for whipping up an assembler or compiler syntax tree in a single weekend. However, when it comes to executing a tight, performance-sensitive VM instruction loop, Python's runtime overhead makes it an impractical choice for simulating a snappy 32-bit architecture.

Why C# and .NET 10 is the "Best of All Worlds"

C# sits perfectly in the goldilocks zone for this project. It is the closest thing to a perfect compromise:

  1. First-Class Unsigned Support: Unlike Java, C# natively supports uint, ulong, and byte straight out of the box. No bit-masking hacks required.
  2. Automatic Memory Management: The garbage collector handles the boring stuff. I can focus on building my compiler's Abstract Syntax Tree (AST) without worrying about manual allocations.
  3. Low-Level Escape Hatches: When the VM instruction loop needs raw speed, C# allows native memory access, pointers, and unsafe blocks. I get high-level productivity with low-level power when it counts.
  4. Ecosystem & Performance: .NET 10 provides incredible first-party libraries, seamless cross-platform execution, and the ability to compile down to native binaries via NativeAOT.
  5. The Familiarity Factor: It is second only to Java for me. The syntax feels like home, meaning I can hit the ground running on day one.

In short, C# is my booster rocket. It’s the highly productive scaffold that will let me build the VM, the assembler, and the compiler quickly. And if everything goes right, it's the very rocket I will ultimately jettison once my own self-hosting language is ready to take over.
